# 依赖管理规范

| 属性 | 内容 |
| --- | --- |
| 状态 | 临时策略，正式发布前必须复审 |
| 适用范围 | 根 Python 与 npm 工具项目 |

Go IAM 实现使用 `platform/iam/go.mod` 与 `platform/iam/go.sum`，两者均跟踪，仓库根目录不建立 Go 模块；`go.sum` 记录模块内容校验值。原有暂不提交 `uv.lock` 和 `package-lock.json` 的决定保持不变。正式发布前仍需完成全仓库依赖可复现性与供应链验收。

IAM 的 Go 清单、校验值和文档工具清单在独立子仓库跟踪；父项目通过 gitlink 锁定它们对应的源码提交，不复制其依赖文件。克隆与 CI 必须初始化这个固定提交，不用 `submodule update --remote` 替换。

## 当前策略

- 提交 `pyproject.toml` 和 `package.json`，把它们作为直接依赖声明。
- 暂不提交 `uv.lock` 和 `package-lock.json`。
- 忽略 `.venv/`、`node_modules/`、包管理器缓存和构建产物。
- Monorepo 子模块不得自行提交重复的根级锁文件。
- CI 使用 `npm install --ignore-scripts --no-package-lock` 安装文档工具。

该策略是项目早期阶段的临时选择，不代表生产发布阶段的最终可复现性方案。

## 已知影响

- 不同时间或环境解析到的间接依赖版本可能不同。
- CI 无法使用要求锁文件的 `npm ci` 或 `uv sync --locked`。
- 上游间接依赖变化可能在未修改仓库代码时改变构建结果。
- 依赖故障排查和历史版本复现成本会增加。

## 复审触发条件

出现以下任一情况时，必须重新评审并优先考虑提交根锁文件：

- 开始实现可部署的平台服务或前端应用。
- 建立正式发布产物、部署包或发布流水线。
- CI 出现由间接依赖漂移导致的不稳定。
- 需要生成软件物料清单、漏洞基线或可审计发布清单。
- 首次发布 MVP、预发布版本或正式版本。

复审后如决定跟踪锁文件，应删除 `.gitignore` 中对应规则，并把 CI 恢复为锁定安装模式。
