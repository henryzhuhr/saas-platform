# 流量路由与发布控制模块需求

| 属性 | 内容 |
| --- | --- |
| 模块 | Routing |
| 工程边界 | `platform/routing` |
| 文档状态 | 草案，待发布、运维、安全与架构评审 |
| 主要需求编号 | `UR-ROUTE-*`、`SR-ROUTE-*` |

## 1. 目标与边界

Routing 模块以产品中立方式管理网络请求应进入哪个应用目标、版本或部署单元，并通过审核、不可变快照、执行面分发和回滚降低发布风险。

负责：

- 网络入口、匹配条件、目标和流量策略的逻辑模型。
- 草稿、校验、影响预览、审核和发布工作流。
- 按租户、标签、名单和稳定规则灰度。
- 不可变发布快照、执行面分发、确认、漂移检测和回滚。

不负责：

- 浏览器页面路由和导航菜单。
- API 网关或流量执行产品自身的运行时实现。
- 应用代码部署、业务健康逻辑和基础设施供应商选型。
- 在每次业务请求中同步查询控制面决定路由。

## 2. 参与角色与依赖

| 参与方 | 主要职责 |
| --- | --- |
| 平台发布人员 | 创建候选、预览、审核、发布和回滚 |
| 业务应用负责人 | 声明入口、目标版本和应用健康条件 |
| 运维人员 | 观察传播、执行面健康、漂移和故障 |
| 安全人员 | 管理高权限发布边界和调查异常变更 |
| Application 模块 | 提供已审核应用版本和流量声明 |
| Tenant 模块 | 提供租户状态、标签和稳定租户集合版本 |
| 网关适配边界 | 转换逻辑快照并操作具体执行面 |
| Audit 模块 | 记录预览、审核、发布、确认和回滚链路 |

## 3. 用户需求

| 编号 | 优先级 | 用户需求 | 详细验收要点 |
| --- | --- | --- | --- |
| UR-ROUTE-001 | P0 | 作为发布人员，我希望集中管理业务应用的流量入口和目标。 | 规则表达入口、匹配条件、目标版本、优先级和必要策略，不泄漏特定网关产品字段。 |
| UR-ROUTE-002 | P0 | 作为发布人员，我希望在发布前校验和预览规则。 | 可发现冲突、歧义、无效目标、越权租户范围和不受支持能力，并预览命中对象和差异。 |
| UR-ROUTE-003 | P0 | 作为发布人员，我希望把已审核配置发布到网关执行面。 | 发布显式、可追踪、可确认；切换边界明确；部分失败不破坏上一有效版本。 |
| UR-ROUTE-004 | P0 | 作为发布人员，我希望快速回滚流量配置。 | 可选择受支持历史快照并重新发布；回滚有影响预览、权限校验和新审计记录。 |
| UR-ROUTE-005 | P1 | 作为发布人员，我希望按租户、标签或显式名单灰度。 | 命中规则确定、稳定、可解释；租户在同一发布版本中不会随机漂移。 |

## 4. 系统需求

| 编号 | 优先级 | 系统行为 | 主要来源 |
| --- | --- | --- | --- |
| SR-ROUTE-001 | P0 | 系统应以产品中立模型管理入口、匹配条件、目标服务、目标版本、优先级和流量策略。 | `UR-ROUTE-001` |
| SR-ROUTE-002 | P0 | 系统应在发布前检查规则冲突、优先级歧义、无效目标、越权范围和执行面能力差异。 | `UR-ROUTE-002` |
| SR-ROUTE-003 | P0 | 规则必须经过草稿、校验、审核和发布状态；执行面只消费已发布完整版本。 | `UR-ROUTE-002`、`UR-ROUTE-003` |
| SR-ROUTE-004 | P0 | 每次发布必须生成不可变版本、内容摘要、来源候选、操作者、审核者和时间。 | `UR-ROUTE-003` |
| SR-ROUTE-005 | P0 | 向任一执行面发布失败时，必须保留上一有效版本，并返回目标级诊断和最终一致状态。 | `UR-ROUTE-003` |
| SR-ROUTE-006 | P0 | 系统应支持回滚到受支持历史快照；回滚必须形成新的候选、发布和审计记录。 | `UR-ROUTE-004` |
| SR-ROUTE-007 | P1 | 系统应支持按租户、租户标签、显式名单和确定性分组规则进行灰度。 | `UR-ROUTE-005` |
| SR-ROUTE-008 | P0 | 执行面不得逐请求同步查询路由控制面，应使用完整、有版本且本地可用的已确认配置。 | `UR-ROUTE-003` |
| SR-ROUTE-009 | P0 | 网关产品差异必须封装在适配边界，不得泄漏到领域模型和应用清单。 | `UR-ROUTE-001`、`UR-ROUTE-003` |

## 5. 状态模型

### 5.1 候选与发布

```text
Draft → Validated → InReview → Approved → Publishing → Published
   │         │          │           │           └──→ Failed
   └─────────┴──────────┴──────────→ Rejected
Published → Superseded
```

- 候选内容在进入审核后冻结；任何修改产生新候选版本。
- `Validated` 只表示静态和能力校验通过，不等于获准发布。
- `Published` 需要满足目标执行面确认策略，不能仅以请求已发送判断成功。
- `Failed` 必须区分未应用、部分应用、确认超时和已自动恢复。
- `Superseded` 历史快照继续保留，用于审计、比较和受支持回滚。

### 5.2 执行面目标状态

每个执行目标至少记录：

- 期望版本和期望摘要。
- 已发送版本、实际确认版本和实际摘要。
- 最后成功时间、最后失败、健康状态和漂移状态。
- 是否继续使用上一有效版本。

控制面必须能区分“发布请求成功”“执行面已接收”“执行面已切换”“业务健康确认”四类状态。

## 6. 规则与灰度不变量

- 同一入口和作用域内的规则优先级必须产生唯一决策；存在歧义时禁止发布。
- 目标应用版本必须已审核且未暂停、未下线。
- 租户匹配只能使用稳定租户标识或有版本的受控标签，不能信任客户端自报标签。
- 灰度分组算法必须确定、可复现并包含规则版本；相同输入得到相同结果。
- 显式排除优先级、显式包含优先级和标签规则优先级必须在契约中固定。
- 发布快照必须完整自包含或明确引用不可变依赖，不能要求执行面拼接多个可变草稿。
- 高权限网关管理凭据只存在于适配执行边界，不进入领域快照和应用清单。

## 7. 失败、回滚与漂移要求

- 发布前必须保存上一有效版本和目标执行面清单。
- 不支持事务切换的多个执行目标必须采用明确的分阶段策略，并暴露部分完成状态。
- 确认超时不得自动视为失败回滚或发布成功；必须先查询实际状态并避免双重操作。
- 自动回滚触发条件、观察窗口和人工覆盖权限必须显式配置并审计。
- 回滚前验证历史目标仍受支持、应用版本仍可用且安全策略未禁止恢复。
- 系统定期比较期望摘要和实际摘要；发现漂移时告警、阻止后续发布或执行受控修复。
- 控制面不可用时，执行面继续使用最后确认配置；控制面恢复后重新对账。

## 8. 验收场景

| 编号 | 场景 | 预期结果 |
| --- | --- | --- |
| AC-ROUTE-001 | 两条规则在同一作用域和优先级命中不同目标 | 校验失败并指出冲突规则，不能进入审核发布 |
| AC-ROUTE-002 | 候选引用已暂停应用版本 | 发布前拒绝并返回无效目标诊断 |
| AC-ROUTE-003 | 发布到执行面并获得匹配摘要确认 | 标记目标成功，记录期望与实际版本及关联审计 |
| AC-ROUTE-004 | 一个执行目标应用失败 | 该目标继续使用上一有效版本，整体状态显示部分失败且可诊断 |
| AC-ROUTE-005 | 相同发布命令因超时被重复提交 | 不产生多个逻辑发布；先对账实际状态再继续处理 |
| AC-ROUTE-006 | 对同一租户重复计算灰度分组 | 在规则版本不变时始终命中同一目标 |
| AC-ROUTE-007 | 回滚到仍受支持的历史快照 | 生成新发布记录，历史快照不被修改，执行面确认新期望版本 |
| AC-ROUTE-008 | 执行面配置被绕过控制面修改 | 对账检测摘要漂移并告警，不把漂移配置登记为合法发布 |
| AC-ROUTE-009 | 控制面故障 | 执行面继续处理业务流量并使用最后确认版本，不逐请求回调控制面 |

## 9. 待确认事项

- 首批入口类型、协议范围、匹配能力和必须支持的流量策略。
- 多执行目标发布的成功判定、原子性边界和自动回滚条件。
- 灰度规则优先级、确定性分组算法和最大租户集合规模。
- 应用健康、业务指标和发布决策之间的责任边界。
- 网关候选产品的快照、确认、回滚、漂移检测和退出能力。
