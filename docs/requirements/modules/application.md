# 应用管理模块需求

| 属性 | 内容 |
| --- | --- |
| 模块 | Application |
| 工程边界 | `platform/application` |
| 文档状态 | 草案，待产品、应用团队与架构评审 |
| 主要需求编号 | `UR-APP-*`、`SR-APP-*` |

## 1. 目标与边界

Application 模块管理业务应用如何注册到平台、声明能力、通过审核、形成版本并向租户开通，使应用团队不修改平台核心代码即可接入和独立演进。

负责：

- 应用稳定身份、所有权、类型和生命周期。
- 版本化应用清单的接收、校验、审核和兼容判断。
- 应用版本、平台契约版本和交付物之间的可追溯关系。
- 应用对租户的开通、暂停和下线范围。

不负责：

- 应用内部业务逻辑、数据模型和页面实现。
- 权限授权、权益计算、导航计算和流量发布的领域状态。
- 直接修改其他模块数据来“完成接入”。
- 规定应用必须使用的语言、框架或部署方式。

## 2. 参与角色与依赖

| 参与方 | 主要职责 |
| --- | --- |
| 业务应用负责人 | 注册应用、提交清单、处理诊断和发起版本审核 |
| 平台管理员 | 审核应用、管理状态和租户开通范围 |
| 租户管理员 | 查看或申请本租户可用应用 |
| IAM 模块 | 校验应用所有权并注册权限命名空间 |
| Entitlement 模块 | 校验权益代码及租户最终权益 |
| Navigation 模块 | 接收已审核导航声明并计算入口 |
| Routing 模块 | 接收已审核流量声明并形成发布候选 |
| Audit 模块 | 记录清单、审核、启停和开通变化 |

## 3. 用户需求

| 编号 | 优先级 | 用户需求 | 详细验收要点 |
| --- | --- | --- | --- |
| UR-APP-001 | P0 | 作为业务负责人，我希望通过版本化清单注册应用能力。 | 清单一次描述应用元数据以及权限、权益、导航、接口、流量和审计声明；具体实现不进入平台领域。 |
| UR-APP-002 | P0 | 作为平台管理员，我希望审核、启用、暂停和下线应用版本。 | 每次变化有前置条件、影响预览和审计；暂停与下线对新开通、导航和流量候选的影响一致。 |
| UR-APP-003 | P0 | 作为业务负责人，我希望平台在生效前发现配置错误。 | 返回可定位字段、错误代码、严重级别和修复建议；一个错误不应掩盖其他可检测问题。 |
| UR-APP-004 | P0 | 作为业务负责人，我希望应用独立版本化和发布。 | 应用版本可独立演进，并记录平台契约兼容范围、内容摘要和交付物来源。 |
| UR-APP-005 | P0 | 作为平台管理员，我希望按租户控制应用开通范围。 | 只有应用、应用版本、租户、订阅和必要权益均有效时才允许开通；重复开通幂等。 |

## 4. 系统需求

| 编号 | 优先级 | 系统行为 | 主要来源 |
| --- | --- | --- | --- |
| SR-APP-001 | P0 | 系统应管理应用稳定代码、名称、类型、所有者、状态和版本，并隔离应用命名空间。 | `UR-APP-001`、`UR-APP-004` |
| SR-APP-002 | P0 | 系统应接收版本化应用清单，并校验 Schema、引用、命名空间、所有权和兼容性。 | `UR-APP-001`、`UR-APP-003` |
| SR-APP-003 | P0 | 应用清单应能声明身份接入、权限、权益、导航、接口、流量和审计能力，但不包含供应商配置秘密。 | `UR-APP-001` |
| SR-APP-004 | P0 | 重复提交相同版本与相同内容必须幂等；相同版本内容不同必须拒绝。 | `UR-APP-003`、`UR-APP-004` |
| SR-APP-005 | P0 | 应用状态变化应一致影响租户开通、导航和后续流量发布，且不能隐式修改已发布历史。 | `UR-APP-002`、`UR-APP-005` |
| SR-APP-006 | P0 | 系统应记录清单版本、内容摘要、提交者、审核者、审核结论和生效状态。 | `UR-APP-002`、`UR-APP-004` |
| SR-APP-007 | P1 | 系统应管理应用版本与平台 API、事件、清单和 SDK 契约的兼容矩阵。 | `UR-APP-004` |

## 5. 状态与不变量

### 5.1 应用状态

```text
Draft → Active ↔ Suspended → Retired
```

- `Draft` 应用只能完善元数据和提交首个版本，不能向租户开通。
- `Suspended` 默认阻止新开通和新发布；既有运行行为必须有明确安全策略。
- `Retired` 不再接受新版本和新开通，但历史记录与兼容信息继续保留。

### 5.2 应用版本状态

```text
Submitted → Validated → InReview → Approved → Active → Deprecated → Retired
     └────────→ Rejected
```

- 清单内容在提交后不可原地修改；修正必须形成新内容版本或新提交。
- 只有通过校验和审核的版本才能进入 `Approved`。
- 同一应用可以保留多个受支持版本，但每个版本的租户范围和发布状态必须明确。
- `Rejected` 必须包含诊断和审核意见，不能进入下游生效流程。
- `Deprecated` 必须说明替代版本和最早停止支持时间。

### 5.3 租户应用状态

```text
Requested → Enabled ↔ Suspended → Disabled
```

- 租户应用关系不能扩大租户本身的订阅、权益或权限。
- 应用暂停、租户暂停或必要权益失效时，最终可用状态必须收窄。
- 关闭应用不能删除其业务数据；数据处理责任由业务应用契约定义。

## 6. 清单和校验要求

应用清单至少具有以下逻辑区域：

- 应用稳定标识、版本、所有者和平台契约范围。
- 权限与服务身份需求。
- 所需或提供的权益定义。
- 页面入口和导航声明。
- 公开 API 资源和网络流量入口声明。
- 审计事件类型、运行指标和必要的数据分类声明。

校验至少覆盖：

- Schema、必填字段、值域和大小上限。
- 应用代码、权限代码、权益代码、事件类型和入口的命名空间所有权。
- 跨模块引用是否存在、版本是否兼容。
- 页面地址与网络路径的格式、冲突和禁止范围。
- 不安全默认值、秘密、生产凭据和不允许的内部实现字段。
- 相同版本内容摘要是否稳定。

## 7. 协调与失败要求

- 应用审核通过不等于所有下游配置立即生效；各模块必须保留独立状态和结果。
- 跨模块接入由应用层协调，通过幂等命令和可靠事件推进，不使用跨模块共享事务。
- 某个下游失败时，应用版本保持可诊断的部分处理状态，但不能被误标记为完全生效。
- 重试必须从已完成步骤继续，不能重复注册权限、权益或入口。
- 下线前必须预览受影响租户、导航、流量、服务身份和契约消费者。

## 8. 验收场景

| 编号 | 场景 | 预期结果 |
| --- | --- | --- |
| AC-APP-001 | 负责人提交格式正确且引用有效的清单 | 生成不可变提交记录、内容摘要和完整校验结果 |
| AC-APP-002 | 相同应用版本和相同内容重复提交 | 返回现有提交结果，不重复触发下游变化 |
| AC-APP-003 | 相同应用版本提交不同内容 | 请求被拒绝并指出版本内容冲突 |
| AC-APP-004 | 清单引用不存在或无所有权的权限代码 | 校验失败，返回具体路径和原因，不进入审核生效 |
| AC-APP-005 | 审核人批准自身无权管理的应用 | 请求被授权层拒绝，版本状态保持不变 |
| AC-APP-006 | 应用版本与平台契约主版本不兼容 | 阻止激活并返回兼容矩阵诊断 |
| AC-APP-007 | 重复为同一租户开通同一应用版本 | 只保留一个有效关系并返回幂等结果 |
| AC-APP-008 | 已暂停应用仍被用于创建新导航或流量发布 | 下游候选校验拒绝，不影响已确认历史记录 |
| AC-APP-009 | 下线应用前执行影响预览 | 返回受影响租户、版本、入口、身份和未完成依赖摘要 |

## 9. 待确认事项

- 首批应用类型、所有权模型和审核职责分离要求。
- 应用清单的格式、Schema 语言、签名和最大尺寸。
- 应用多版本并行、租户版本选择和弃用窗口。
- 应用暂停时既有流量应立即阻断、保持只读还是由策略决定。
- 应用数据导出、删除和租户关闭时的责任契约。
