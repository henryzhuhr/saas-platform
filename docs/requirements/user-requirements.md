## 1. 文档职责

本文定义产品级目标、目标用户、核心旅程、范围和跨模块体验原则。每个领域的详细用户故事、业务规则、异常场景和验收场景拆分到[模块需求](modules/README.md)，避免一份文档同时承担产品总览和领域规格。

需求层次如下：

```text
产品目标与角色
  → 核心用户旅程
  → 模块用户需求 UR-*
  → 模块系统需求 SR-*
  → 验收场景 AC-*
  → 契约、实现与自动化测试
```

本文和模块文档共同构成用户需求基线，不能只阅读本文就假设已经获得全部领域细节。

## 2. 产品定位

SaaS Platform 是面向多个业务应用的统一 SaaS 控制面。它管理身份、租户、访问规则、产品订阅、租户权益、应用接入、导航入口、网络流量发布和审计治理，使业务团队不必重复建设通用平台能力。

平台不是业务功能集合。业务应用继续拥有自己的业务流程、业务数据、业务接口和发布节奏，并通过公开 API、事件、应用清单和 SDK 接入平台。

## 3. 业务目标

### 3.1 平台运营目标

- 在统一入口完成租户开通、成员治理、订阅配置、应用开通和运行状态查看。
- 使产品、套餐、权益和应用版本的生效过程可预览、可追踪、可解释。
- 将高风险变更纳入明确授权、审核、发布、回滚和审计流程。
- 在租户数量增长时保持标准化运营，不依赖逐租户修改代码或手工部署。

### 3.2 租户体验目标

- 用户通过统一身份进入其有权访问的租户和业务应用。
- 同一用户加入多个租户时，始终明确当前租户和当前权限范围。
- 租户管理员能够自助管理成员、角色、应用入口和本租户配置。
- 页面展示、后端授权和订阅权益使用一致规则，并能解释拒绝原因。

### 3.3 业务应用目标

- 业务应用通过版本化契约声明权限、权益、导航、流量和审计需求。
- 新应用接入和既有应用升级原则上不修改平台核心领域代码。
- 业务接口获得可信身份与租户上下文，并能执行一致的权限和权益判断。
- 应用拥有独立版本和发布节奏，同时可追溯到平台契约兼容范围。

### 3.4 安全与运营目标

- 默认阻断跨租户访问，异常租户不能无边界影响其他租户。
- 身份撤销、权限撤销和租户停用在明确时间内对运行时生效。
- 关键操作、安全事件、发布结果和跨模块流程可关联追踪。
- 控制面短时故障时，运行时继续使用安全且已确认的有效状态。

## 4. 目标用户与职责边界

| 角色 | 主要目标 | 允许范围 | 不能默认拥有的能力 |
| --- | --- | --- | --- |
| 平台管理员 | 管理平台全局配置和租户生命周期 | 经授权的跨租户管理、应用治理和平台策略 | 查看任意业务数据或绕过审计 |
| 平台运营人员 | 管理产品、套餐、订阅和运营配置 | 商业化配置及租户开通 | 管理身份凭证或发布流量规则 |
| 平台发布人员 | 管理流量配置、灰度和回滚 | 经审核的发布工作流 | 修改业务数据或直接绕过发布快照 |
| 安全与审计人员 | 调查安全事件并验证控制有效性 | 按职责查询审计、安全和访问证据 | 默认修改生产配置或用户授权 |
| 租户管理员 | 管理本租户成员、角色和体验配置 | 当前租户内的授权管理 | 跨租户操作或授予平台级权限 |
| 租户成员 | 使用获准业务能力 | 当前租户内已授权、已开通的功能 | 通过隐藏入口或直接 URL 绕过授权 |
| 业务应用负责人 | 注册、升级和运营业务应用 | 自有应用命名空间及已授权发布范围 | 读取平台内部存储或其他应用私有配置 |
| 运维人员 | 保证容量、稳定性和恢复能力 | 受控运行操作、隔离、恢复和诊断 | 无审批读取敏感业务内容 |
| 服务身份 | 执行非人工系统调用 | 明确授权的应用、租户和操作范围 | 继承自然人全部权限或长期不可撤销访问 |

同一自然人可以承担多个角色，但每次操作必须以当前会话、当前租户和当前授权为准，不能因为其在其他租户或其他职责中拥有权限而扩大本次访问范围。

## 5. 核心用户旅程

### 5.1 租户开通与首次使用

```text
平台创建租户
  → 指定首位租户管理员
  → 开通产品和订阅
  → 计算功能权益与资源配额
  → 启用业务应用
  → 邀请成员并分配角色
  → 用户验证身份并选择租户
  → 用户访问获准应用
```

旅程必须支持失败重试、重复请求去重、部分步骤待处理和完整审计。任一步骤失败都不能留下无法识别归属或无法继续处理的租户状态。

### 5.2 业务应用接入

```text
业务负责人提交版本化应用清单
  → 平台校验格式、命名空间、引用、兼容性和安全约束
  → 负责人修正诊断或提交审核
  → 管理员审核应用版本
  → 租户获得应用开通范围
  → 导航和流量配置形成候选版本
  → 已发布配置进入运行时
```

应用未通过审核、已暂停、已下线或与平台契约不兼容时，不能继续产生新的生效配置。

### 5.3 登录与业务访问

```text
验证主体身份
  → 建立受保护会话
  → 确定唯一当前租户
  → 验证有效成员关系
  → 计算权限与策略
  → 计算租户权益和配额
  → 返回应用入口和导航
  → 业务 API 再次执行授权与资源租户归属检查
```

导航不可见、权限拒绝、权益不足和资源不属于当前租户是不同拒绝原因，面向用户时应给出安全、可操作且不泄露敏感信息的说明。

### 5.4 订阅变更

```text
运营人员创建订阅变更
  → 预览生效时间和权益差异
  → 审核高风险降级或终止
  → 按约定时间切换订阅状态
  → 重新计算权益和配额
  → 通知受影响应用与运行时视图
  → 记录执行结果和异常
```

升级、降级、续期、暂停和终止必须具有明确的时间语义，不能通过修改历史套餐版本改变已生效事实。

### 5.5 灰度发布与回滚

```text
创建候选应用或流量版本
  → 配置租户范围、标签或显式名单
  → 预览命中范围和规则冲突
  → 审核并发布不可变快照
  → 观察版本、租户和错误指标
  → 扩大范围、暂停或回滚
```

发布失败不能破坏上一有效版本；回滚是一次新的、可审计的发布操作，不修改历史记录。

### 5.6 安全事件响应

```text
检测异常或接收报告
  → 定位主体、租户、应用和关联操作
  → 撤销会话、凭证或授权
  → 隔离异常租户或应用
  → 验证运行时传播结果
  → 保留调查证据并恢复正常状态
```

安全人员必须能判断控制动作是否已传播完成；传播超时不能被静默视为成功。

## 6. 模块需求地图

| 模块 | 用户需求范围 | 主要用户结果 | 详细文档 |

| 身份与访问管理 | `UR-IAM-*` | 安全登录、可信身份、会话和授权 | [IAM](modules/iam.md) |
| 租户、组织与隔离 | `UR-TEN-*` | 租户生命周期、成员管理和隔离 | [Tenant](modules/tenant.md) |

| 权益与配额 | `UR-SUB-003` 至 `UR-SUB-006` | 功能开通、配额和最终权益 | [Entitlement](modules/entitlement.md) |
| 应用管理 | `UR-APP-*` | 应用注册、审核、版本和租户开通 | [Application](modules/application.md) |
| 导航管理 | `UR-NAV-*` | 可见、稳定、可解释的页面入口 | [Navigation](modules/navigation.md) |
| 流量发布控制 | `UR-ROUTE-*` | 可预览、可回滚的网络流量发布 | [Routing](modules/routing.md) |
| 审计与运营治理 | `UR-AUD-*`、`UR-OPS-*` | 可追溯、可诊断、可治理的运行状态 | [Audit](modules/audit.md) |

## 7. 跨模块体验原则

### 7.1 一致与可解释

- 同一状态在管理界面、运行时接口和审计记录中必须使用一致含义。
- 拒绝结果应区分身份无效、成员关系无效、权限不足、权益不足、租户状态异常和资源归属不符。
- 管理员应能预览高影响变更的对象范围、时间和预期结果。
- 异步操作必须展示当前状态、成功结果、失败原因和可采取的下一步。

### 7.2 安全默认值

- 未明确授予权限、未明确开通权益或无法确认租户归属时默认拒绝。
- 用户不能通过客户端参数、页面地址或自定义请求切换到无权访问的租户。
- 高权限和跨租户操作必须比普通租户操作具备更强授权和审计。
- 面向终端用户的错误不能泄露其他租户、主体或内部拓扑信息。

### 7.3 可恢复与可操作

- 可重试操作必须避免重复创建、重复扣减或重复发布。
- 关键配置必须保留可识别的上一有效状态。
- 失败必须可定位到具体步骤、对象和关联标识，不能只返回模糊的整体失败。
- 删除、停用和下线必须区分可恢复阶段与最终不可逆阶段。

### 7.4 规模化自助

- 常见租户开通、成员管理、订阅变更和应用开通应提供批量或自动化入口。
- 列表、导出和搜索必须适用于大租户，不能要求一次加载全部对象。
- 平台运营流程不能依赖为每个租户修改代码、创建独立分支或手工修改网关配置。

## 8. 优先级和发布口径

| 优先级 | 含义 | 发布处理 |
| --- | --- | --- |
| `P0` | 平台能力基线；缺失时无法形成安全、完整的首个可用闭环 | 必须在对应里程碑退出前完成或经正式决策调整 |
| `P1` | 稳定版本前的高价值能力；可以晚于首个闭环，但不能被静默忽略 | 纳入明确里程碑并定义兼容扩展点 |
| `P2` | 后续增强；由真实业务、合规或规模证据驱动 | 不预先实现，但不得通过当前设计永久阻断 |

优先级表示业务必要性，不等同于开发顺序。安全基础、数据边界和契约兼容能力即使用户界面较晚提供，也必须在底层设计阶段考虑。

## 9. 范围边界

### 9.1 当前平台能力基线

- 身份、认证、会话、服务身份、角色、权限和强化认证。
- 租户生命周期、成员、组织、可信租户上下文和隔离策略。
- 产品、功能、不可变套餐版本、订阅、权益和资源配额。
- 应用清单、版本、审核、启停和租户开通范围。
- 页面导航和基于应用、权限、权益及租户配置的可见性计算。
- 网络流量规则的草稿、校验、审核、不可变发布、分发和回滚。
- 平台审计、安全事件、跨模块关联和租户级运营治理。
- 版本化平台接口、事件、应用清单和至少一种接入 SDK。

### 9.2 当前不包含

- 支付收单、财务账单、税务、开票和对账。
- 具体业务应用的数据模型、业务流程和业务页面。
- 完整低代码平台、通用工作流引擎或应用市场交易能力。
- 所有身份协议、所有 SDK 语言和所有部署环境的一次性支持。
- 未由法规、地域和业务连续性目标驱动的跨地域多活。

不在当前范围不表示架构可以阻断未来能力；数据所有权、契约版本和扩展点必须允许后续演进。

## 10. 规模与成功标准

设计容量基线是至少 10,000 个活跃租户和 1,000,000 个注册用户。该数字表示系统容纳的对象规模，不等于同时在线人数或每秒请求数。

产品成功至少满足：

1. 所有 P0 用户需求都映射到系统需求和可执行验收场景。
2. 新业务应用只依赖公开契约完成接入，不读取平台内部数据结构。
3. 用户在任何操作中都具有唯一可信租户上下文，跨租户访问默认拒绝。
4. 权限、权益、导航和网络流量路由分别计算、分别解释，不能相互替代。
5. 最大租户或异常租户不能无边界占用共享资源。
6. 控制面短时不可用时，已确认的运行时状态继续安全工作。
7. 关键状态变化、发布结果和安全控制动作可以追踪、验证和恢复。

## 11. 假设与待确认事项

| 主题 | 当前假设 | 需要确认的决策输入 |
| --- | --- | --- |
| 首批应用 | 多个业务应用共享平台能力 | 应用数量、类型、流量入口和接入顺序 |
| 租户规模 | 10,000 活跃租户，租户规模高度不均衡 | 最大租户成员量、应用量和流量占比 |
| 身份 | 同时存在自然人和服务身份 | 首批身份源、联合和生命周期同步需求 |
| 订阅 | 平台管理订阅事实，不承担支付结算 | 首期人工开通还是对接外部订单系统 |
| 隔离 | 支持共享、独占和混合策略抽象 | 数据等级、法规、地域和商业隔离等级 |
| 运行目标 | 当前数值是内部设计基线 | 对外 SLA、审计留存、RPO 和 RTO 承诺 |
| 前端集成 | 业务应用通过稳定入口接入 | 页面集成模式、跨应用体验和品牌定制范围 |

## 12. 需求维护规则

- 详细需求以模块文档中的稳定编号为准；本文只维护产品级上下文和索引。
- 已被引用的需求编号不得重用或静默删除；废弃时保留状态、原因和替代编号。
- 用户目标变化时先更新用户需求，再更新系统需求、架构、契约和测试。
- 需求必须描述可观察结果，不把未经选择的产品或实现方式写成用户需求。
- 新增模块前先确认其业务边界、数据所有权及与现有模块的区别。
- 每次需求评审同步更新[需求追踪矩阵](traceability.md)和相关验收场景。
