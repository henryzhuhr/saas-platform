# 项目结构与模块边界

| 属性 | 内容 |
| --- | --- |
| 状态 | 草案，待工程架构评审 |
| 原则 | 领域边界与部署边界分离、技术中立、契约优先 |

## 1. 仓库结构

```text
saas-platform/
├── api/                    # 公开接口、事件和应用清单契约
├── applications/           # 接入平台的业务应用
├── build/                  # 构建元数据与发布产物规则
├── deploy/                 # 部署、环境和运行拓扑定义
├── docs/                   # 需求、架构、标准和 ADR
├── frontend/               # 租户门户、平台控制台和公共前端能力
├── platform/               # 平台控制面领域与应用逻辑
│   ├── iam/                # 身份与访问管理
│   ├── tenant/             # 租户、成员、组织与隔离策略
│   ├── subscription/       # 产品、套餐版本与订阅
│   ├── entitlement/        # 权益、配额与用量语义
│   ├── application/        # 应用注册、版本与开通范围
│   ├── navigation/         # 导航树与可见性计算
│   ├── routing/            # 网络流量规则与发布控制
│   └── audit/              # 审计与运营治理
├── scripts/                # 仓库级开发、校验和维护工具
├── sdk/                    # 业务应用接入 SDK
├── services/               # 可部署入口和基础设施适配
│   ├── platform-api/       # 平台接口、聚合和用例协调入口
│   └── gateway-adapter/    # 网关产品适配与配置发布边界
└── tests/                  # 集成、端到端、容量、安全与恢复测试
```

当前只创建职责清晰的目录和说明，不用空实现预设编程语言、框架、存储、网关或部署平台。

目录中的 README 是面向项目成员的局部说明和导航入口。其设计背景见 [ADR-0001](decisions/0001-repository-knowledge-and-readme-map.md)。

## 2. 三类边界

### 2.1 领域边界

`platform/` 按业务语义组织，拥有领域模型、用例接口和数据所有权。领域代码不关心进程启动、网络协议、数据库驱动或供应商客户端。

### 2.2 部署边界

`services/` 定义进程入口、协议适配、依赖装配和运行配置。一个部署单元可以组装多个领域，也可以只承载一个领域；实际拓扑由容量与可靠性证据决定。

### 2.3 契约边界

`api/` 和 `sdk/` 保存跨团队、跨进程或跨版本协作所依赖的稳定契约。内部目录结构不能成为业务应用的隐式 API。

## 3. 平台与业务应用

### 3.1 `platform/`

平台目录只包含 SaaS 控制面公共能力。任何新增模块必须满足：

- 被多个业务应用复用，或属于平台统一治理职责。
- 拥有可清楚描述的数据和行为边界。
- 不包含具体业务应用的实体、页面和流程。
- 可以通过版本化接口、事件或清单提供能力。

### 3.2 `applications/`

每个业务应用拥有自己的后端、前端、数据变更、测试和交付扩展。业务应用：

- 通过平台契约获取身份、租户、权限和权益上下文。
- 在自身数据访问中执行租户隔离。
- 声明权限、权益、导航、接口、流量和审计能力。
- 不直接读取平台内部存储或依赖平台内部类型。

## 4. 平台模块职责

| 模块 | 负责 | 不负责 |
| --- | --- | --- |
| `iam` | 身份、认证、会话、角色、权限、策略、服务身份 | 订阅、权益、导航、业务数据 |
| `tenant` | 租户、成员、组织、标签、生命周期、隔离策略 | 凭证、产品套餐、业务资源 |
| `subscription` | 产品、功能、套餐版本、订阅状态和周期 | 支付、财务账单、用户授权 |
| `entitlement` | 租户权益、配额、覆盖、用量语义 | 角色权限、业务计费、导航结构 |
| `application` | 应用、版本、清单、审核、状态、租户开通 | 业务实现和业务数据 |
| `navigation` | 应用入口、导航树、排序、可见性和解释 | 后端授权、网络流量路由 |
| `routing` | 流量规则、灰度策略、发布快照、分发和回滚 | 网关运行时实现、页面路由 |
| `audit` | 审计契约、关键事件、完整性、查询和留存 | 普通调试日志、业务分析仓库 |

IAM 是 NIST 术语库收录的“身份与访问管理（Identity and Access Management）”缩写，不是具体产品名称，来源见 [NIST IAM Glossary](https://csrc.nist.gov/glossary/term/Identity_and_access_management)。

## 5. 依赖方向

```text
frontend / applications
        ↓
public contracts / sdk
        ↓
services composition
        ↓
platform application interfaces
        ↓
platform domain models
        ↓
infrastructure adapters
```

约束如下：

1. 领域模块不依赖 `services/`、`frontend/` 或具体基础设施实现。
2. 业务应用不依赖 `platform/` 内部代码，只依赖公开契约和 SDK。
3. 模块之间通过应用接口或版本化事件协作，不直接连接其他模块存储。
4. 网关、存储、缓存、事件和身份供应商客户端属于适配器。
5. 跨模块工作流由应用层协调，不把协调逻辑塞入领域实体。
6. 发现循环依赖时应重新划分边界或引入稳定契约，不通过共享数据库绕过。

## 6. `services/` 说明

### 6.1 `platform-api`

对平台管理和运行时查询提供统一入口，负责：

- 协议转换、输入校验和错误映射。
- 身份上下文验证和用例授权。
- 跨领域用例协调与聚合视图。
- 追踪、审计关联和运行配置。

该目录不表示所有领域必须永久部署在一个进程中。

### 6.2 `gateway-adapter`

负责把平台流量发布快照转换为所选网关执行面的配置，并隔离：

- 供应商模型和管理接口。
- 高权限管理凭据。
- 能力差异、发布确认和错误映射。
- 配置预览、原子切换和回滚实现。

网关尚未选型，因此当前只定义抽象边界。

## 7. 面向规模的工程约束

- 租户数据从第一版起包含稳定分区或隔离维度。
- 对外服务不依赖进程内唯一状态，允许横向扩展。
- 列表、导出、审计和批处理都有界，禁止全租户同步扫描。
- 消息和任务处理具备幂等、去重、重试、背压和租户公平性。
- 高频授权、权益、导航和流量读取使用可重建的版本化派生视图。
- 容量测试覆盖大租户、突发租户、异常租户和故障恢复。

## 8. 目录演进规则

- 新增一级目录或平台模块前，先更新需求、本文和必要 ADR。
- 只有出现独立容量、可用性、数据或团队边界时才新增部署单元。
- 目录重命名必须同步公开契约、文档地图和迁移说明。
- 具体技术选择不得写成领域目录职责。
- 重要的历史结构决策即使被替代也保留 ADR。

## 9. 后续工作

1. 评审用户需求、系统需求、容量和 SLO 基线。
2. 定义应用清单、平台接口和事件契约的第一版。
3. 为身份、权威存储、状态传播、网关和部署平台分别形成选型 ADR。
4. 用容量原型验证分区、授权读取、撤销传播和流量发布。
5. 根据验证证据决定实际服务拓扑和首批实现顺序。
