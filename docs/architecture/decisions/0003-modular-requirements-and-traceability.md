# ADR-0003：模块化需求与稳定追踪关系

| 属性 | 内容 |
| --- | --- |
| 状态 | Proposed |
| 日期 | 2026-07-17 |
| 范围 | 用户需求、系统需求、平台模块、验收场景和后续契约 |
| 关联文档 | `docs/requirements/`、`platform/`、ADR-0001 |

## 1. 背景

首版需求把所有用户需求集中在 `user-requirements.md`，把所有功能、数据、接口和非功能系统需求集中在 `system-requirements.md`。该方式便于快速建立全局基线，但随着 8 个平台领域逐渐详细化，出现以下问题：

- 单份文档同时承担产品总览、领域规格和验收清单，阅读成本持续上升。
- 一个模块的用户故事、系统行为、状态机和异常场景分散在多个长章节中。
- 工程人员从 `platform/<module>/` 进入时，无法直接定位该模块的完整需求。
- 用户需求到系统需求只有示例映射，无法机械检查 P0 需求是否存在验收场景。
- Subscription 和 Entitlement 首次共同建模，需求编号前缀不能准确表达后续明确的数据所有权。

需求仍处于首次正式评审前，但已经被架构、规范依据和模块 README 引用。因此，重构必须改善边界，同时保持已建立编号稳定。

## 2. 决策

采用三层需求结构：

```text
docs/requirements/
├── user-requirements.md       # 产品目标、角色、旅程和范围
├── system-requirements.md     # 跨模块规则、接口、数据和 NFR
├── modules/
│   ├── README.md              # 模块需求地图
│   ├── iam.md                 # 模块用户需求 + 系统需求 + 验收场景
│   ├── tenant.md
│   └── ...
└── traceability.md            # UR → SR/NFR → AC 映射
```

### 2.1 根用户需求

根用户需求只维护：

- 产品定位、业务目标和目标角色。
- 端到端用户旅程和跨模块体验原则。
- 平台范围、优先级、规模和待确认业务问题。
- 详细模块需求的导航。

### 2.2 根系统需求

根系统需求只维护：

- 系统边界和全局架构约束。
- 跨模块 API、事件、数据所有权和一致性规则。
- 容量、性能、可用性、安全等非功能需求。
- 全局交付、运行和系统验收基线。

### 2.3 模块需求

每个 `platform/` 领域对应一份模块需求文档。该文档把同一领域的用户需求和系统需求放在一起，并至少包含：

- 目标、负责范围和非目标。
- 参与角色和上下游依赖。
- 稳定编号的用户需求与功能系统需求。
- 状态模型、领域不变量和失败原则。
- 数据、接口、传播、安全和审计要求。
- 可转化为测试的 `AC-<DOMAIN>-NNN` 验收场景。
- 待确认事项和后续契约输入。

### 2.4 追踪矩阵

使用独立追踪矩阵维护：

```text
UR-* → SR-* / NFR-* → AC-* → 后续契约 / ADR / 自动化测试
```

模块文档是需求正文的权威来源，追踪矩阵只维护关系，不复制需求正文。

### 2.5 编号稳定性

- 已有 `UR-*`、`SR-*` 和 `NFR-*` 编号保持不变。
- 需求迁移到模块文档不视为语义替代，不创建新编号。
- `UR-SUB-003` 至 `UR-SUB-006`、`SR-SUB-003` 至 `SR-SUB-006` 和 `SR-SUB-008` 归入 Entitlement，但保留历史前缀。
- 后续新增权益需求使用 `UR-ENT-*` 和 `SR-ENT-*`。
- 废弃需求保留编号、状态、原因和替代项，不重用编号。

## 3. 被否决的备选方案

### 3.1 继续维护两份超长需求文档

否决原因：模块上下文分散、局部评审成本高，状态机和验收场景会继续挤压产品级信息，最终难以保持可导航性。

### 3.2 按模块分别建立用户需求目录和系统需求目录

示例：

```text
user/iam.md
system/iam.md
```

否决原因：同一领域的用户目标、系统行为和验收场景仍然分离，评审时需要在两个目录来回跳转，边界变化容易只更新其中一份。

### 3.3 每个模块建立 README、用户需求和系统需求三份文件

否决原因：当前每个领域的规模尚不足以证明三份文件的维护成本合理；目录和索引数量显著增加，需求映射仍需第四个来源。未来单个模块文档过大时可以在保持索引和编号规则的前提下进一步拆分。

### 3.4 重排全部需求编号以匹配新模块

否决原因：已有编号已被架构和规范依据引用。重排会破坏历史追踪，并使后续无法区分“需求语义变化”和“文档移动”。

## 4. 后果

### 4.1 正面影响

- 产品人员可以从根用户需求理解全局目标，不必加载全部系统细节。
- 模块负责人可以在一份文档中评审用户目标、系统行为和验收结果。
- 工程目录可以直接链接到对应模块需求，边界和需求更接近。
- P0 用户需求是否有系统行为和验收场景变得可检查。
- 后续 API、事件、ADR 和测试可以在稳定需求编号上继续扩展追踪关系。

### 4.2 成本与风险

- 新增需求时需要同步模块文档和追踪矩阵。
- 跨模块需求需要判断应由根系统需求还是某个权威模块拥有。
- 模块文档可能再次增长，需要定期评估是否按子能力拆分。
- 当前追踪矩阵是 Markdown，尚未提供机器可读 Schema 和完整性检查器。

## 5. 约束

1. 根用户和系统需求不得重新复制全部模块需求正文。
2. 模块文档不得把具体框架、数据库、网关或部署产品写成未确认需求。
3. 同一功能系统需求只能有一个权威模块所有者。
4. 跨模块流程在追踪矩阵中可以映射多个系统需求，但不能通过共享数据所有权解决。
5. 所有 P0 用户需求至少映射一个功能系统需求和一个验收场景。
6. 新增、废弃或改变需求语义时，同一变更更新追踪矩阵。
7. 需求目录继续遵守 ADR-0001 和 Markdown 文档地图规则。

## 6. 迁移方式

1. 将根用户需求改为产品目标、角色、旅程和模块索引。
2. 将根系统需求改为跨模块能力、数据规则和非功能基线。
3. 把 8 个领域的现有 `UR-*` 和 `SR-*` 移入对应模块文档。
4. 为状态、不变量、失败和验收场景补充详细描述。
5. 建立追踪矩阵，并验证现有编号没有丢失或重复定义。
6. 更新 `platform/`、架构地图和需求地图的入口链接。

## 7. 后续演进

- 为需求元数据和追踪关系定义机器可读格式，并由 CI 检查编号唯一性和 P0 覆盖率。
- 在 M1 契约设计中增加 API、事件、应用清单和 SDK 对应关系。
- 实现后增加测试标识、实现版本和验证证据。
- 单个模块文档过大时，通过新 ADR 或本文的兼容扩展规则拆分为子模块索引。
