# ADR-0002：技术中立且规模优先的架构基线

| 属性 | 内容 |
| --- | --- |
| 状态 | Accepted |
| 日期 | 2026-07-16 |
| 决策范围 | 需求、架构、项目结构和后续技术选型 |

## 背景

项目早期讨论以若干技术产品和部署方式作为说明示例。初始文档把其中部分示例写成了既定架构，包括把 APISIX 固定为 API 网关、把 Helm 固定为部署包，并预设首期采用模块化单体。这些内容来自参考输入或早期推演，没有经过正式技术选型。

这些内容没有经过技术选型，也不是用户确认的约束。继续保留会造成以下问题：

- 把参考输入误当成已确认决策。
- 需求描述实现方式，而不是用户目标和系统能力。
- 候选方案无法基于容量、安全、可靠性和运维约束公平比较。
- 更换供应商会影响领域模型、应用清单和大量文档。
- “万级租户、百万级用户”缺少可验证的容量和 SLO 基线。

## 决策

### 1. 需求与逻辑架构技术中立

规范性需求和总体架构只使用逻辑角色，例如：

- `API 网关 / 流量执行面`，不使用具体网关产品代替。
- `权威存储`、`缓存`、`状态传播`，不预设数据库或消息产品。
- `部署平台`、`发布产物`，不预设编排平台和包格式。
- `访问凭证`、`会话`，不预设 Token 结构或传递方式。

产品名称只能出现在对应选型 ADR、适配器实现文档和验证报告中。

### 2. 保留有来源的专业术语

专业术语不是供应商选型。项目保留以下有明确来源的术语，但首次出现时提供中文解释；完整出处见[项目术语表](../../requirements/glossary.md)：

- 身份与访问管理（Identity and Access Management，IAM）。
- 基于角色的访问控制（RBAC）。
- 权益（Entitlement）。
- 服务等级指标与目标（SLI / SLO）。
- 恢复点与恢复时间目标（RPO / RTO）。

OAuth、OpenID Connect 等开放协议可以作为标准参考，但是否成为强制支持项仍需通过需求和 ADR 确认。

### 3. 领域边界与部署边界分离

不预先决定模块化单体或微服务数量。先稳定身份、租户、订阅、权益、应用、导航、流量和审计等逻辑边界，再根据容量测试、故障域、数据一致性和团队所有权决定物理部署。

### 4. 采用规模优先基线

系统从设计起至少支持：

- 10,000 个活跃租户。
- 1,000,000 个注册用户。
- 5,000,000 条租户成员关系。
- 1,000,000 个同时有效会话。

总用户量不等于峰值并发或 QPS。正式性能验证必须建立具体负载模型，并分别测量登录、授权、权益、导航、管理、事件传播和流量发布。

### 5. 选型由约束和证据驱动

身份、存储、缓存、事件、网关、部署和可观测性选型必须：

1. 引用已确认的功能与非功能需求。
2. 比较至少两个可行方案或说明为何只有一个方案可行。
3. 验证关键容量、延迟、故障和运维场景。
4. 记录选择、代价、风险、迁移和退出策略。
5. 形成独立 ADR 后才能进入项目基线。

## 被否决的方案

### 把早期示例直接作为默认技术栈

否决原因：示例没有经过约束分析和容量验证，会把偶然输入固化为长期依赖。

### 需求文档同时维护多套具体实现

否决原因：需求会快速膨胀并混淆“必须具备的能力”和“如何实现”。具体方案比较属于 ADR 或验证报告。

### 先固定微服务拆分再补充容量依据

否决原因：服务数量不能直接解决规模问题，还会提前引入网络、数据一致性和运维复杂度。逻辑边界应稳定，部署边界由证据决定。

### 只写百万用户，不定义派生容量和 SLO

否决原因：注册用户数无法推导并发、吞吐、数据量和恢复目标，无法用于设计或验收。

## 影响

### 正面影响

- 需求可长期稳定，不随供应商和部署方式变化。
- 后续技术方案可以基于同一组规模和质量目标比较。
- 网关、存储和状态传播实现被限制在适配边界内。
- 领域模型和业务应用契约更容易保持可移植。
- 容量与可靠性目标可以直接映射到测试和验收。

### 代价

- 在技术 ADR 完成前，不能直接开始依赖具体基础设施的实现。
- 需要额外建立负载模型、原型验证和选型矩阵。
- 适配边界和契约设计比直接调用供应商接口需要更多前期工作。

## 历史说明

本决策接受后，APISIX、Helm 和模块化单体从规范性需求及总体架构的默认实现中移除。它们仍可作为未来候选方案参与选型，但不具有默认优先级，也不能因为曾在参考输入中出现而跳过方案比较和规模验证。
